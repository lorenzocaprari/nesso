# Benchmarks

Use a Release build. `NESSO_TRACE=1` prints one JSON line on stderr per command, with per-stage microseconds and peak RSS:

```bash
NESSO_TRACE=1 ./build/Release/src/nesso grep "connection refused" /var/log/app.log --model-dir models/
```

`NESSO_FORCE_KERNEL` pins the float distance kernel for tests and benchmarks. It is read once, on the first distance calculation in the process. `scalar` uses the scalar kernel. `avx2` uses AVX2+FMA when the CPU supports both, and the scalar kernel otherwise, so it does not execute AVX2 instructions the CPU lacks. An unset variable, an empty value, or any other value keeps automatic selection (AVX2+FMA when the CPU supports both, otherwise scalar). Leave it unset for that automatic kernel. Command output is unchanged.

`scripts/profile` runs the same command under `perf` and `heaptrack` and writes `build/profile/flamegraph.svg` and `build/profile/heaptrack-summary.txt`. It needs `perf`, `heaptrack`, and FlameGraph's `stackcollapse-perf.pl` and `flamegraph.pl` on `PATH`, or `NESSO_FLAMEGRAPH_DIR` set to a FlameGraph checkout:

```bash
./scripts/profile grep "connection refused" /var/log/app.log --model-dir models/
```

`scripts/bench` times `grep` on fixed-seed synthetic logs of 1k, 10k, and 100k lines and writes `bench/results/<sha>.json`. The result records the CPU model, `nproc`, and `NESSO_THREADS`. `scripts/bench-compare` fails when wall time or peak RSS is more than 15% above [bench/baseline.json](../bench/baseline.json):

```bash
python3 scripts/bench
python3 scripts/bench-compare
python3 scripts/bench --dataset logdir
python3 scripts/bench --ttfa
python3 scripts/bench --dataset real-log
python3 scripts/bench-real-log-compare --result bench/results/<sha>.real-log.json
```

`bench/baseline.json` is the committed shared-runner sample. Replace it on purpose with `bench-baseline`, which keeps the slower wall time of each tier when given more than one result:

```bash
go run -C scripts/ci . bench-baseline --output bench/baseline.json bench/results/<sha>.json
```

`python3 scripts/bench --dataset logdir` generates a seeded synthetic log directory and writes `bench/results/<sha>.logdir.json`. The tree has syslog files and two rotations, an auth log, kernel and boot logs, a cron log, a package-manager log, a JSON Lines application log, a journal text export, and small non-log files under `etc/`, `proc/`, and `sys/`. The lines are templates filled from a fixed seed. Nothing in the tree is downloaded or committed. `--lines` sets the line count (default 256). `--mib` grows the indexed files to that many MiB instead. `nesso index` reads regular files, so the run passes every file in the tree. The result records the index wall time, the first search wall time, their sum, peak RSS, the line count, the file count, and the corpus-to-input byte ratio, plus the CPU model, `nproc`, and `NESSO_THREADS`.

`python3 scripts/bench --ttfa` (same as `--dataset ttfa`) generates a seeded synthetic support-style bundle directory and writes `bench/results/<sha>.ttfa.json`. The tree has rotated plain logs, a `.gz` log, a JSON Lines file, an extensionless journal export, and a `.tar.gz` whose members are more generated logs. Gzip and tar bytes use fixed `mtime=0` metadata so a given seed is byte-identical. Nothing in the tree is downloaded or committed. `--lines` sets the line count (default 256). `--mib` grows the on-disk files to that many MiB instead. The run passes the bundle directory as the single `nesso index` path so directory walk and in-place `.gz` / `.tar.gz` reads are exercised; the archive is not extracted. Each timed command gets a fresh empty `XDG_CACHE_HOME`. The result records the index wall time, the first search wall time, their sum, peak RSS, the line count, the file count, and the corpus-to-input byte ratio, plus the CPU model, `nproc`, and `NESSO_THREADS`. This mode is report-only: it is not part of the Pipeline `bench` job and is not compared against `bench/baseline.json`.

`python3 scripts/bench --dataset search-profile` indexes one seeded log and times one `nesso search`. Non-query lines carry a letter id so the template mask does not collapse them. The timed search sets `NESSO_TRACE=1`. The stages `corpus-read`, `query-embed`, and `distance` are the corpus read, the ONNX query embedding, and the distance scan. `model-load` is the ONNX session load and is recorded on its own. The script runs that search again with `NESSO_TRACE` empty and fails when stdout differs. With `NESSO_TRACE` unset, nesso does not print those timings. `--lines` sets the log size (default 1000). The result is `bench/results/<sha>.search-profile.json`. It is not part of the Pipeline `bench` job and is not compared against `bench/baseline.json`.

`python3 scripts/bench --dataset real-log` times `nesso index`, `nesso grep`, `nesso search`, and `nesso search --mode dense` on the first 1000000 lines of HDFS_v1, BGL, and Thunderbird (`REAL_LOG_DEFAULT_LINES` in `scripts/bench`), from Zenodo record 8196385. Masked dedup embeds one line per distinct masked text, so a repeated template is embedded once. Available corpora are HDFS_v1 (`block replication`), BGL (`kernel fatal`), and Thunderbird (`authentication failure`). The default is `hdfs-v1,thunderbird`: HDFS is a cheap smoke; Thunderbird is the peak-RSS / wall canary. Pass `--corpora all` (or `hdfs-v1,bgl,thunderbird`) to include BGL. The logs come from `scripts/fetch-loghub` in [nesso-bench](https://github.com/lorenzocaprari/nesso-bench), which downloads each archive, checks its sha256, writes the pinned 1M-line prefix, and deletes the archive. `scripts/bench` does not download: it reads `--loghub-dir` (default `build/bench`), and a missing log is an error that prints the nesso-bench command to run, for example `python3 ../nesso-bench/scripts/fetch-loghub --dataset thunderbird --dest-dir build/bench`. Thunderbird is read from the tar member and is never extracted. The lines are real log lines. A short file is an error. Nothing is repeated, and nothing is committed. Each selected set runs at `NESSO_THREADS=1` and `NESSO_THREADS=8`. Every command sets `NESSO_TRACE=1`. The result is one file, `bench/results/<sha>.real-log.json`, with wall time, lines per second, peak RSS, input bytes, corpus bytes, and the trace stages. `--lines` sets the prefix length for every selected corpus. The run truncates the 1M-line prefix.

`scripts/bench-real-log-compare` reads that JSON. Peak RSS is a hard failure when any command is above 1.5 GiB times `(1 + NESSO_BENCH_RSS_TOLERANCE)`. The nightly workflow sets that tolerance to `0.15`. Wall time is compared with the median of earlier results for the same corpus, prefix length, thread count, and command, and only prints a warning. `--history` reads an earlier real-log result JSON or a `{"runs": [...]}` list of them. A missing history prints a warning and exits 0.

[`.github/workflows/bench-real-log.yml`](../.github/workflows/bench-real-log.yml) runs this on the schedule `47 5 * * *` (main only) and on `workflow_dispatch` (any branch, for a manual check). Nightly uses `hdfs-v1,thunderbird`. Manual runs can set the `corpora` input to `all` or another comma-separated list. It does not run on pull requests, and it does not change the Pipeline `bench` job or `bench/baseline.json`. From Actions, open **Real-log bench**, choose **Run workflow**, pick the branch, and optionally set `corpora`, `force_log_refetch` (ignore the truncated-log cache), or `nesso_version`. An empty `nesso_version`, including every scheduled run, builds HEAD. A release version such as `0.3.1` skips that build: `scripts/fetch-released-nesso` downloads `nesso_<version>_amd64.deb`, checks it against the release `SHA256SUMS`, and the benchmark runs the unpacked `usr/bin/nesso` with the MiniLM files shipped in `usr/share/nesso`. The job timeout is 300 minutes. Each command has a 2400-second timeout, which only catches a hang. The workflow checks out nesso-bench at `NESSO_BENCH_REF`, the same commit [eval-retrieval](../.github/workflows/eval-retrieval.yml) pins, and fetches with its script. The truncated logs are cached by corpus set and that script's contents. A cold Thunderbird run downloads that archive (about 2 GiB) and deletes it after the prefix is written. The gate step downloads the `real-log-bench` artifact of the latest successful scheduled run on `main` and passes it as `--history`. The measure job needs `contents: read`, `packages: read`, and `actions: write` (the log cache).

The `bench` CI job runs on every pull request, on pushes to `main`, and nightly. Pull requests time the 1k and 10k tiers. Pushes to `main` and the nightly schedule also time 100k. The job compares the tiers it ran with `bench/baseline.json` and fails when wall time is more than 1.35× the baseline or peak RSS is more than 1.15× the baseline (`NESSO_BENCH_WALL_TOLERANCE`, `NESSO_BENCH_RSS_TOLERANCE`). A missing baseline file fails the job. The same job runs the 4000-line grep once with `NESSO_THREADS=1` and once with `NESSO_THREADS=4` and fails unless the 4-thread run is at least `threadScaleMinRatio` faster (`scripts/ci`). The job summary lists lines per second for each tier and that ratio. The baseline is the only stored result; no benchmark history is recorded. That sample is the Ubuntu GCC 15 Release binary (`build-gcc-26-amd64`, profile `gcc-26`). EL9 release builds use GCC Toolset 16.2.1 (`gcc-26-el9`, `gcc-26-el9-armv8`). The Clang lanes and clang-tidy use Clang 23.1.6 (`clang-26`, `clang-26-asan`, `clang-26-tsan`). Ubuntu 26.04 CI stayed on GCC 15, because Resolute's `gcc-16` package is a trunk snapshot, not GCC 16.2. A later move of this baseline's wall time or peak RSS is a nesso change or a runner change, not that toolchain switch.

Google Benchmark microbenchmarks build with `-o "&:bench=True"` on the Release profile and produce `build/Release/bench/nesso_bench`. That binary times the scalar and AVX2+FMA dot-product and squared-L2 kernels on 384-dimensional vectors (`DotProduct384Scalar`, `DotProduct384Avx2Fma`, `L2Squared384Scalar`, `L2Squared384Avx2Fma`). The AVX2+FMA cases skip when `SelectDistanceKernel("avx2", ...)` would not select that kernel.

## Retrieval evaluation

Retrieval quality and the comparison with other tools live in [nesso-bench](https://github.com/lorenzocaprari/nesso-bench): the harness (`eval-retrieval`, `eval-retrieval-compare`, `eval-retrieval-merge`), the Loghub 2k seed sets, the needle queries on the labelled Loghub 2.0 windows, the competitor stacks (grep, ripgrep, SQLite BM25, a FAISS stack, OpenSearch, xerj, ck, vecgrep), the manual Eval competitors workflow, and the committed competitor reference reports. Its [docs/eval.md](https://github.com/lorenzocaprari/nesso-bench/blob/main/docs/eval.md) describes the metrics, the engines, `--measure`, and the fairness rules. The benchmarks above stay here: they measure nesso against its own earlier builds.

To score a local build, clone nesso-bench next to the build and point it at the binary and the model. Missing Loghub inputs are downloaded under nesso-bench's `build/bench/` and checked against their pins:

```bash
git clone https://github.com/lorenzocaprari/nesso-bench
python3 nesso-bench/scripts/eval-retrieval --dataset all-2k \
  --engine nesso --engine grep --engine bm25 \
  --binary build/Release/src/nesso --model-dir models --out build/eval/all_2k.json
```

[`.github/workflows/eval-retrieval.yml`](../.github/workflows/eval-retrieval.yml) runs that report with nesso, grep, and BM25 on the 2k seed sets (`all-2k`) and on the Hadoop, OpenStack, and HealthApp 2k sets (`all-formats`, a separate report so the six original sets stay comparable), plus the `bgl-needle-100k` needle window and `thunderbird-needle-1m` with nesso (`auto`, `dense`, `lexical`), grep, and BM25. `thunderbird-needle-1m` is the only Thunderbird needle dataset at the pinned nesso-bench commit: 1,000,000 lines of Loghub 2.0 Thunderbird starting at line 8,550,001, fetched with `scripts/fetch-loghub --dataset thunderbird-loghub2 --window 8550001:1000000`. That commit defines no Thunderbird 100k needle window. Every run scores only nesso-bench's dev queries (`--split dev`): its test queries are frozen and are read for releases and the published scorecard, not while the ranking changes. It checks out nesso-bench at the commit in the workflow's `NESSO_BENCH_REF` and builds nesso. A `workflow_dispatch` input `nesso_version` (for example `0.3.1`) skips that build and scores the released `.deb` instead, including both speed measurements; `eval-pipeline` is ignored for that run so the release is not reported as this commit. An empty `nesso_version`, and the schedule, still build HEAD. When the Pipeline push run for the same commit uploaded `eval-pipeline`, this workflow reuses those nesso reports (wrapped to schema 4 by `scripts/eval-wrap-nesso-report`), scores only grep and BM25, and merges them; otherwise it scores nesso too (`--jobs 4`). `eval-pipeline` has no Thunderbird report, so nesso is scored on `thunderbird-needle-1m` on every run, together with grep and BM25, at `--jobs 4`. It runs on schedule `47 6 * * *` (main only) and on `workflow_dispatch`. Pull requests are scored by the Pipeline `eval-retrieval` job instead (below). To take a nesso-bench change, bump `NESSO_BENCH_REF` to the nesso-bench commit in its own pull request; that pull request's Pipeline `eval-retrieval` job shows any score change the bump brings. After scoring, the same job measures that same nesso binary, BM25, and grep on the `bgl-needle-100k` window and on `thunderbird-needle-1m` with `eval-retrieval --measure --measure-only` (mode `auto`, `NESSO_THREADS=1`, 3 repeats) and writes the medians, ranges, peak RSS, and the nesso / BM25 and nesso / grep ratios to the job summary and the `eval-retrieval-measure` artifact (`scripts/eval-measure-summary`). Each window is its own `continue-on-error` step. The BGL measure is a few minutes and the eval job timeout is 120 minutes. The numbers depend on the runner, are for development only, and gate nothing. Every run compares the pin with nesso-bench's `main` and emits a warning annotation, also written to the job summary, when the pin is behind `main` or not on it. The check never fails the run.

Each run downloads the `eval-retrieval` artifact from the latest successful scheduled run on `main` and compares the 2k, formats, BGL needle, and Thunderbird needle reports with it (`eval-retrieval-compare --previous`). It emits a warning annotation when a score drops by more than 5% relative to the previous value. For MRR, the summary also shows how sure that change is. For each class whose per-query MRR moved, it gives a paired bootstrap 95% interval of the change and a verdict (`better`, `worse`, or `within noise`), and it lists the queries that moved, with first-hit ranks for a needle report. When the previous run scored a different query set for a class, for example after nesso-bench grew its sets, that row says so instead of giving a verdict. An MRR warning carries the same interval or query-set note, because on a small class one query is enough to cross 5%. The job summary also shows nesso's MRR margin over the best other engine per system and class (`eval-retrieval-compare --margins`): the candidates are grep and BM25 scored in the same run on the same queries, and each margin carries a paired bootstrap 95% interval and a win, tie, or loss verdict. nesso-bench's committed competitor references are not used here, because they were scored on an older query set and record no split. Scores never fail the job; only script errors do. This nightly workflow is not a Pipeline job and not part of the `CI gate`, and it does not write `gh-pages`.

The Pipeline job `eval-retrieval` (in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml), part of the `CI gate`) is the retrieval quality gate. It runs on every event that runs the heavy jobs, so a docs-only pull request skips it. It scores the `build-gcc-26-amd64` Release binary with nesso only, on the dev queries of `all-2k`, `all-formats`, and `bgl-needle-100k` (`auto`, `dense`, `lexical`; no `hybrid`), with nesso-bench `--jobs 4` (each search child gets `NESSO_THREADS=1`), and uploads the three reports as `eval-pipeline` (kept 90 days) together with the host record from `scripts/eval-host`.

Dense scores are not comparable across CPUs. ONNX Runtime 1.18 picks its int8 GEMM kernel from the CPU after nesso refuses AMX tile data: AVX-512 VNNI when that flag is present, otherwise AVX2. The float ops around that GEMM are not the same bytes on those two kernels, so a near-tie in dense ranking can move. The float distance kernel (`NESSO_FORCE_KERNEL`) is AVX2+FMA on both of those CPUs, so pinning it does not make the two reports comparable. The job therefore scores the baseline Release binary on the same runner as the head. It downloads that run's `release-build` archive (kept 1 day) or, once the archive has expired, checks out the commit and builds it with `-o tests=False`. The summary names the CPU, the distance kernel, and the int8 kernel, and says both sides used this runner. `build/eval/current/host.json` in the artifact is that same record.

The baseline commit is the pull request's merge base on `main`, the parent of a push to `main`, or, when that commit cannot be resolved, the latest push run on `main` that still has a Release archive (`fallback`). A missing archive does not change the commit: the job builds it.

The job summary also shows the per-query section and the `DROP` and `WORSE` lines of `eval-retrieval-compare`. Only a pull request compared with its merge base can fail: `--fail-on-worse` exits 3 when a nesso ranker's per-query MRR or nDCG@10 got worse beyond noise (the paired bootstrap 95% interval lies below 0) in a class whose query set did not change. One query moving in a small class, a changed query set, a fallback baseline, and a push to `main` only warn. When a regression is the intended trade-off, add the label `eval-regression-accepted` to the pull request and re-run the job: it reads the labels when it runs and then only warns. The job restores the Loghub caches that the nightly workflow saves and downloads any input that is missing.

nesso-bench owns `scripts/fetch-loghub`; this repository has no copy. The eval, real-log, and Pipeline workflows pin the same nesso-bench commit (`NESSO_BENCH_REF`; a unit test checks the three match), so the query sets and the logs always come from one commit. Bump all three in one pull request.
